# Inactive migration openings

The opening operator supports separately approved inactive migration openings. Installation, a configuration flag or a signed design document does not authorize financial application. Ordinary funding remains disabled by default. BILLmanager retains authority until a separately accepted handover.

Opening proofs are root-owned ordinary 0600 files in root-owned private 0700 directories. Symbolic links, stream wrappers, hard links, unknown schemas, duplicate decoded JSON keys, float financial values and changed byte hashes are rejected. Root-owned sticky system temporary ancestors may contain the private directory; its ancestors must not otherwise be group/other writable. Public application source contains no signer, private signing key or approval generator.

External attestation uses a detached RSA-SHA256 signature over original payload bytes and public RSA keys of at least 3072 bits. Signature schema 1 contains `schema_version`, `key_id`, `algorithm` (`rsa-sha256`) and strict `signature_b64`. Trust schema 1 has purpose `opening-trust`, keys keyed by issuer ID with `issuer`, public PEM `public_key` and purpose allowlist `purposes`, plus `revoked_keys` and `revoked_nonces`. Every payload binds schema, purpose, issuer, exact UTC `not_before` / `expires_at`, and nonce. All fields are required; unknown fields are denied. Financial values are strings.

Accepted purposes are `account-funding-release`, `account-opening-fence`, `opening-backup-acceptance`, `billmanager-inactive-opening-approval`, and the separate `account-funding-runtime-acceptance`. Their exact closed schemas are validated by `ProofSchema`. Runtime acceptance cannot approve initialization.

The external fence custodian must control every source financial writer, incoming payment/notification boundary, and target writer. The signed `account-opening-fence` lease binds source population, exact target/baseline, freeze ID, monotonic sequence and writer/notification fingerprints. It lasts at most 60 seconds and must be renewed outside the operator's network namespace. The custodian must keep writers fenced until the operator exits or is fenced, including after lease expiration. A signed lease represents verified custodian evidence; the operator does not freeze a source itself or contact providers.

Opening uses a genuine Linux root Artisan invocation, separate outbound-disabled network namespace and authenticated local Unix database socket. No web route, cron or queue entry may borrow it. A manifest pins all installed source/dependency bytes and persisted configuration. Only non-executable logs, cache data and session data in the exact signed generated paths are excluded; executable files there cause denial. Source snapshots, approval records and actual account lists belong outside Git.

Read-only preparation consumes schema 1 `billmanager-inactive-opening-input`: source identity/timezone, original login cutoff, frozen rolling two-year activation cutoff, exact import ID, complete proposed scope and checksum-bound snapshot/checksum/policy/population-review references. The population review must enumerate selected accounts and all currently eligible source accounts/users; the external fence later binds its exact bytes, so unseen additions cannot be silently dropped. Account ownership and original encrypted archive lineage are checked against the selected import and original mappings.

The command is `php artisan billmanager:openings:prepare <input-manifest> --report=<new-private-file>`. It creates only a private report; it does not create an import, wallet, credit or authorization. A separate executable bundle binds that completed report and its input, target inventory/full SQL/cold restore acceptance, release and freeze proofs, exact candidate scope and its fingerprint. This two-stage structure avoids circular report/bundle hashes. Archived retention is never advanced to discard history. An eligible account's owner must also meet the frozen two-year login rule; provisional/postpaid/inactive/currency/duplicate/reservation exceptions stay blocked.

Target inventory covers every table/view row and definition, allocator state, routines, triggers and events. Raw cells are type-tagged/base64-encoded to preserve binary values, decimal strings and duplicate multiplicity. No session or ticket table is exempted. Only exact, verified database batch/receipt/wallet/projection deltas are permitted. Complete cold-restore acceptance binds original full SQL and the exact dump binary/options; a report or checksum alone is not restore acceptance.


Held openings use a typed permission bound to one inactive evidence object, the original database connection and live transaction. It allows only the native wallet and exact nonnegative cash projection; every original migration hold remains in place. Generic credit model events also require the same pending, validated projection object. Ordinary funding rejects this temporary authority, regardless of the process-local enabled flag. The previous funding configuration and container binding are restored on every exit.

For schema 1, the source capture must fall inside the original signed writer-fence window. Keep the original receipt immutable. For continuing external lease renewal, configure `ACCOUNT_OPENING_FENCE_INDEX_PATH` to a root-owned `0600` reference in a root-owned `0700` directory. Its closed schema is `schema_version=1`, `purpose=account-opening-fence-reference`, and `payload`/`signature` references, each containing a sibling absolute `path` and exact `sha256`. The independent custodian writes a new immutable signed pair first and atomically replaces the reference afterward. The reference selects a signed lease; it grants no authority itself. Every use still verifies signature, expiry, revocation, original freeze/population/target and controlled writer boundaries. Existing fixed lease paths are supported for coordinated updates. The custodian must retain the writer fence until the operator exits or is externally fenced, even if a lease expires.

## Applying and recovering an approved batch

Install the opening schema before capturing the complete baseline. Configure `ACCOUNT_OPENING_JOURNAL_DIRECTORY` to a root-owned private directory and retain it with the original immutable bundle, external approval and backups. The application has no command to issue these approvals or control source writers.

Run `php artisan billmanager:openings:apply <bundle> --approval=<approval> --signature=<detached-signature> --report=<new-private-file>` in the accepted isolated root environment. Both an exclusive filesystem lock and a database session lock protect the entire invocation. Each native wallet, cash projection and immutable account receipt commits together. Wallets remain inactive, with every migration hold preserved. Completion seals the batch; sealing does not enable spending or billing.

Before each account transaction, the operator fsyncs an attempt record containing exact scope and bounded allocator budgets. This private hash-chained journal explains only possible rolled-back ID allocations. It never proves a payment or opening. The database batch pins its original path, device, inode and header hash. Missing, replaced, truncated or unexplained records deny further application. No repair or ignore-journal option is provided.

After interruption, retain the original evidence and obtain a current lease for the same externally maintained writer fence. Re-run the same apply command with a new report path. Original committed receipt and wallet IDs are verified and retained; only uncommitted approved accounts can be initialized. A sealed batch cannot be applied again. Changed target rows, source facts, ownership, exclusions, activated wallets or allocations outside the journal budget cause denial without repairing them.

Run `php artisan billmanager:openings:verify <bundle> --report=<new-private-file>` to export database-derived evidence without opening accounts. Verification needs the original bundle, journal and fence-verification public trust, but does not require current opening approval. Revoking an approval cannot erase its existing receipts. Report files are exclusively created as root-owned `0600` files; existing files are never overwritten. If export fails after a commit, apply returns failure and the database receipts remain authoritative. Verify before deciding whether to resume.

These commands expose aggregate results only. There are no activation, hold-release, freeze, handover or database-restore options. A whole-database rollback is unsuitable after live financial activity; recovery then requires a separately reviewed forward procedure.

### Later ordinary runtime acceptance

Holding/opening release acceptance and later `account-funding-runtime-acceptance` are distinct. The latter uses a root-owned 0640 service-readable proof/public-trust/manifest set under root-owned non-writable ancestors and binds the accepted handover decision plus current installed bytes, configuration and authenticated runtime/database target. It does not grant `inactive_opening`, initialize wallets, release holds or activate facilities. Ordinary workers need no root opening-console privilege. Defaults remain disabled/unset; an external custodian must supply later acceptance after separately approved handover. See `docs/account-funding.md` for exact configuration.

### Isolated acceptance and recovery evidence

The operator acceptance runs on a separately owned Linux runtime and local database socket in an outbound-disabled namespace. It retains complete original SQL, installed-file and configuration digests, all holds, the original signed bundle/approval, the allocator journal and persisted account receipts. Proofs generated by test fixtures are fictional; they confer no real opening or handover authority.

Isolation checks capture regular, synchronous, after-response and batched Bus dispatches, both sent and queued Mail, attempted HTTP calls and configured provider invocations. Each channel is deliberately injected once and must fail its own exact assertion even when the jobs table remains empty. All original tables, schemas, allocators, routines, triggers and events remain identical; only the four receipt-verified opening/projection tables may change.

Complete preactivation recovery requires an actual cold database restart, full canonical SQL checksum equality and fresh native readback of the same authenticated target, configuration, installed files and holds. A new payment, renewal, settlement or activated wallet makes whole-database restoration ineligible. Preserve forward financial receipts and use separately authorized accounting reconciliation instead. A snapshot or generated backup signature alone is not cold-restore acceptance.

The test-only cold probe requires an explicitly supplied root-private `OPENING_COLD_RESTORE_PROBE` executable script and an owned `OPENING_FIXTURE_ROOT`. It validates the isolated testing context before creating artifacts and supports synthetic snapshot/restore actions only. No application command exposes restore, activation, freeze, signing or hold-release capabilities.

Before publication, retain a genuine half-cohort interruption and fresh-process resume with the original receipt IDs, independent four-decimal integer arithmetic, exact original-history exclusions and unchanged holds, together with focused/full-suite and format results. Recovery and publication acceptance remain separate from real deployment, opening and billing handover.

Keep funding disabled, mail in the array transport and jobs synchronous in the owned fixture environment. Retain its complete zero-skip native suite evidence, independent cohort verification and actual cold restoration as mandatory publication gates. Ordinary CI alone cannot replace them. The opening journal records a bounded initial batch allocation before its first insert as well as account allocations; a rolled-back initial batch may resume only that original approved bundle, with every other row/schema and full baseline SQL preserved except its proved allocation counter.

### Capture and opening-readiness protocol (schema 2)

The [capture/readiness design](superpowers/specs/2026-10-14-source-capture-opening-readiness-design.md) separates capture from later opening readiness. Capture leases bind observed runtime and control identities before snapshot, population, refreshed baseline or operator namespace exist. Completed capture acceptance binds the resulting original snapshot/population and collector receipt. The first ready lease follows completed native preparation and backup acceptance and binds the actual later isolated root operator. The application verifies this evidence; it does not issue it or install physical controls.

Schema-1 preparation inputs and original executable/receipt contracts retain their existing behavior. A schema-2 executable bundle adds these five required fields: `source_capture_id`, `control_epoch_sha256`, `capture_fence_sha256`, `capture_acceptance_sha256`, and `preparation_history_sha256`. It also adds exactly eight checksum-bound references: `control_epoch`, `capture_fence`, `capture_fence_signature`, `collector_receipt`, `capture_history`, `capture_acceptance`, `capture_acceptance_signature`, and `preparation_history`. Its existing `freeze_receipt`/`freeze_signature` identify the original v2 ready pair. Capture acceptance and first-ready evidence are distinct from the separately signed v2 human inactive-only approval, which also binds the five lineage fields and exact original bundle, scope and accounts.

The external custodian publishes a closed schema-2 `account-opening-fence-reference` with sibling `payload`, `signature` and `history` references. Each reference contains only absolute `path` and original `sha256`. V2 requires this pointer and never falls back to a fixed pair or v1 pointer. Publish/fsync a new immutable signed pair and complete history, then atomically replace the pointer and synchronize its directory before acknowledgment. Retain every ancestor pair and the selected immutable history indexes.

History starts with capture sequence one and exact null predecessor. Every later sequence is contiguous and binds the predecessor's original payload SHA. UTC and observer-monotonic intervals must overlap or meet, with nondecreasing UTC and strictly increasing observer counters. Capture cannot follow readiness. The same epoch, source/runtime, writer and incoming-payment boundaries remain fixed; ready renewals also preserve original population, baseline, actual operator and capture/preparation lineage. Current selection must extend both the original preparation prefix and every already selected or durably recorded history prefix. A still-live older pointer or substituted same-sequence proof denies. Source and observer monotonic domains are checked separately and never subtracted from each other.

Control reads are bounded before allocation: 64 KiB per payload, signature, epoch or collector; 4 MiB per history index; 32 MiB combined unique original control bytes; 10,000 leases and eight reference levels. Ordinary-file owner, mode, ancestry, device/inode, hardlink and open/read stability checks remain mandatory. Large snapshot, population, preparation, financial approval, SQL, inventory and installed-file manifest retain their separate existing contracts. Exhausting a control bound denies authority without rolling an epoch or repairing evidence.

V2 receipts retain exactly `schema_version=2`, `payload_b64`, `signature` and checksum-bound `history` under existing `delta.fence_proof`. The original payload/signature must equal the checked historical head; decoded payload is at most 65,536 bytes and canonical base64 at most 87,384 bytes. Receipt creation must lie inside its recorded lease. Immediately before commit, both the freshly selected live head and the exact recorded receipt head must still be valid; renewal cannot retroactively replace a receipt's evidence. No financial schema or allowed delta is widened.

Read-only committed-receipt verification checks complete historical capture/readiness lineage and current trust/revocation at internally recorded creation times. It does not need a live lease, current pointer or new human approval merely to read committed facts. Apply/resume still requires current live evidence, the original human approval, exact original batch/bundle/journal and continuous history. Missing or revoked evidence denies verification/application without deleting, rewriting or repairing financial records. New epoch, capture, baseline or approval cannot silently resume an old batch. Sealed replay and restoration after live financial use remain denied.
