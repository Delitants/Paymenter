# Scheduler/process adapters Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement and natively rehearse selective scheduler suppression and cgroup-v1 process containment exclusively on fictional, independently owned Linux guest resources.

**Architecture:** Add a separate finite rehearsal dispatcher, exact-byte scheduler adapter, identity-bound process adapter, persistent start guard and independent observer to the external toolkit. A host harness owns an offline, version-matched guest and records crash/reboot and retirement evidence. Existing fictional boundary registration and native opening proof acceptance remain unchanged.

**Tech Stack:** Python 3.10+ standard library and unittest; QEMU x86_64 TCG as the current host is a different architecture; version-matched Linux kernel, systemd and Cronie; an independently built Python 3.11 guest runtime if the legacy image lacks Python 3.10+.

**Spec:** [Approved scheduler/process specification](../specs/2026-10-07-scheduler-process-adapters-design.md), SHA256 `d5ac6ee6b9fca2860a7b0c48a3ed537b50f009881ff05b3b4e2c2504858f1297`.

## Global Constraints

- Fixed adapter operations only on independently owned fictional resources in a disposable, version-matched Linux guest. No mutation of source/target configuration, cron, process, service or filesystem. Separately bounded read-only metadata/preservation probes remain permitted outside the adapter dispatcher.
- Every aggregate result keeps `enforcement_complete=false` and `real_execution_ready=false`. Rehearsal success never accepts a production plan or all seven boundaries.
- Rehearsal adapter IDs are exactly `scheduler-selective-v1-rehearsal` and `process-freezer-v1-rehearsal`. The existing boundary evaluator remains restricted to `fixture-boundary-v1`.
- Fixed operation names are `inspect`, `prepare`, `establish`, `readback`, `recover`, and `release`. No shell/SQL snippets, executable choices, dynamic imports or extra QEMU arguments in profiles.
- Existing boundary plan/witness/reference schemas, native `ProofSchema`, signing/trust and Paymenter application files remain unchanged.
- Private evidence inside the guest is ordinary root-owned 0600 files beneath root-owned 0700 directories. Host evidence is owner-only 0600 beneath owner-only 0700 directories; host root is never required.
- No symlink/hard-link traversal, existing-evidence overwrite, duplicate decoded JSON keys, unknown fields, floats, bool-as-int, cyclic references or path substitution.
- Limits: 4 MiB per document, 32 MiB combined document graph, 10,000 combined entries and eight reference levels, including witness references and rollback bytes. Binary guest image/package assets are separately bounded and hash-pinned.
- Pin the actual accepted kernel build and scheduler/service package revisions, not merely cgroup v1 availability. No cgroup-v2 Docker result can accept this native increment.
- Guest has no outward network access, source disk/socket, provider credentials, real cron/service roots or customer VM attachment. Repository code never executes as production host root.
- Maintain at least 1 GiB root and 512 MiB RAM reserve outside staging. No skip, omitted case, timeout-only denial or unrelated setup failure proves acceptance.
- No automatic thaw, cron restoration or restart on expiry, controller/observer death, disconnect or reboot. Guard denial precedes billing startup; boot change invalidates witnesses.
- BILLmanager remains authoritative. No real freeze, opening, hold release, credit application, mail/provider operation, activation, deassignment or handover.
- Native inline execution remains selected; after implementation, one fresh independent whole-branch reviewer checks the immutable candidate.

## Review Focus

1. A stale or same-byte-substituted ownership/rollback file must reject before touching a guest or scheduler target (Tasks 1–3).
2. Shared jobs, environment-changing cron syntax and an already dequeued worker must not disappear behind a successful selective edit (Tasks 3 and 6).
3. A thread or child outside the freezer, a reused PID, or inherited frozen ancestry must prevent false containment or unsafe release (Task 5).
4. Missing/corrupt guard state, a service alias and early reboot dispatch must deny before fixture execution while unrelated startup works (Tasks 4 and 7).
5. Disk exhaustion, observer/controller death or partial release must latch failure, retain evidence/denial and externally fence the fictional opening operator (Tasks 2, 6 and 7).

### Closed rehearsal documents

All following documents have `schema_version=1` and the stated distinct `purpose`. Exact keys are required, all hashes are lowercase 64-digit hex, identifiers use `[A-Za-z0-9_.-]{1,128}`, and decimal strings are canonical unsigned values of at most 32 digits. References have exactly `path`, `sha256`. No constructor performs I/O.

- Common `context` keys: `plan_sha256`, `adapter_manifest_sha256`, `member_manifest_sha256`, `session_id`, `freeze_id`, `control_id`, `control_generation`, `source_boot_id`. Generation is a positive non-bool integer below `2**63`; IDs and boot identity use existing validators. `source_boot_id` denotes the fictional guest boot and must never be taken from a production observation as authorization.
- `source-control-adapter-runtime`: keys `schema_version`, `purpose`, `runtime_id`, `architecture`, `kernel_release`, `kernel_sha256`, `systemd_package`, `cronie_package`, `selinux_mode`, `python_sha256`, `qemu_sha256`, `qemu_img_sha256`, `base_image_ref`, `assets`, `files`, `tool_sha256s`. Architecture is `x86_64`; SELinux mode is `enforcing`, `permissive` or `disabled`, matching accepted platform metadata. Asset rows have `asset_id`, `path`, `sha256`, `bytes`, `provenance_ref`; file rows have `asset_id`, `relative_path`, `sha256`, `bytes`, `mode`. These are data-only authenticated offline inputs, not a package installer or executable-selection interface. Host paths must remain inside the explicitly owned runtime root. No URL or fetch occurs in the harness. `base_image_ref` must match one declared binary asset; images/RPMs are not parsed as 4 MiB JSON documents. Individual assets and the complete staged allocation are bounded by the 8 GiB harness cap and remaining reserve. Provenance references are ordinary bounded documents, with exactly `schema_version`, `purpose=source-control-adapter-provenance`, `publisher`, `artifact_id`, `artifact_sha256`, `verification_method`, `verification_ref`; method is `publisher-signature` or `authenticated-publisher-checksum`, with original verification bytes privately referenced.
- `source-control-adapter-ownership`: keys `schema_version`, `purpose`, `guest_id`, `session_id`, `runtime_sha256`, `base_image_sha256`, `host_process`, `guest_boot_id`, `guest_nonce_sha256`, `resource_refs`. `host_process` has `pid`, `start_identity`, `exe_sha256`, `argv_sha256`; `start_identity` is the platform's bounded process-creation identity, independently reread with PID/executable/QMP UUID before any signal. Resource rows have `resource_id`, `kind`, `relative_path`, `device`, `inode`; kinds are `overlay`, `seed`, `qmp`, `channel`, `evidence`. Fresh nonce material stays private and is bound to the harness-created seed and guest handshake, not accepted from a caller's boolean claim.
- `source-control-adapter-bootstrap`: keys `schema_version`, `purpose`, `guest_id`, `session_id`, `nonce`, `runtime_ref`, `tools_ref`; nonce is a newly generated 256-bit lowercase hex value, kept private. The read-only seed carries this document and fixed bootstrap code; no operator-supplied script field exists. `tools_ref` points to a manifest with exactly `schema_version`, `purpose=source-control-adapter-tools`, `files`; each file row has `relative_path`, `sha256`, `bytes`, `mode` and is on the compiled generic toolkit/fixture allowlist. The harness records newly created resource identities before launch in a private intent; ownership_ref is finalized only after UUID/nonce/runtime/guest boot are independently checked. Reset creates a new ownership document for the new boot, retaining the same owned host process identity and original prior ownership references.
- `source-control-adapter-request`: keys `schema_version`, `purpose`, `operation`, `adapter_id`, `context`, `ownership_ref`, `runtime_ref`, `scope_ref`, `precondition_refs`, `rollback_ref`, `release_ref`. `rollback_ref` is null only for inspect/prepare; `release_ref` is non-null only for release. All request references are purpose/slot checked. Host requests are sent only through the exact harness-owned guest channel; no CLI accepts SSH hosts or live roots.
- `source-control-adapter-scope`: keys `schema_version`, `purpose`, `context`, `scheduler_files`, `tasks`, `launchers`, `unrelated`, `unresolved`. Scheduler rows have `object_id`, `relative_path`, `original_sha256`, `uid`, `gid`, `mode`, `metadata_ref`, `entry_spans`. Each span has `object_id`, `start`, `end`, `sha256`; offsets are non-bool byte integers with `0 <= start < end`. Task rows have `object_id`, `identity`, `domain_sha256`, `original_membership_ref`. Identity keys are `boot_id`, `pid`, `tid`, `start_ticks`, `exe_sha256`, `uid`, `gid`, `ppid`, `controller_path_sha256`. Launcher rows have `object_id`, `launcher_id`, `bytes_sha256`, `dependencies_ref`; launcher IDs are compiled fictional entry points, never command strings. Unrelated rows have `object_id`, `evidence_ref`; unresolved rows have `object_id`, `reason_code`, `evidence_refs`.
- `source-control-adapter-evidence`: keys `schema_version`, `purpose`, `kind`, `context`, `observer_identity`, `interval`, `resource_manifest_sha256`, `facts`, `refs`, `errors`. Kinds are `precondition`, `metadata`, `original-membership`, `rollback`, `intent`, `physical-readback`, `attempt`, `unrelated`, `failure`, `release-authority`. Pre-plan metadata may have null context/observer/interval; every post-intent fact is fully context-bound. Fact rows have `object_id` (nullable), `fact_code`, `value`; errors have `object_id` (nullable), `reason_code`. Facts use a finite per-kind code/type allowlist, not arbitrary nested objects or assertion text. Bool fact codes are `reload_seen`, `dispatch_denied`, `guard_denied`, `work_acknowledged`, `operator_fenced`, `operator_retired`, `opening_committed`, `boot_changed`, `rollback_verified`. Hash codes are `installed_sha256`, `metadata_sha256`, `task_identity_sha256`, `membership_sha256`; `counter_value` is a nonnegative decimal string; `freezer_state` permits only THAWED/FREEZING/FROZEN. State facts alone never establish coverage. Add no fact code without its explicit test and typed implementation-plan amendment. Kind/slot requirements are: metadata and rollback reference the exact metadata/original documents; original-membership references the exact membership document; intent binds original refs with no positive gate assertion; physical-readback carries installed/membership hashes and effective states; attempt requires dispatch/guard denial or work acknowledgement plus counter; unrelated requires work acknowledgement plus counter; release-authority requires current operator fenced/retired, opening_committed false, and the accepted generation. Failure carries coded errors, never a passing gate assertion.
- `source-control-adapter-file-metadata`: keys `schema_version`, `purpose`, `object_id`, `uid`, `gid`, `mode`, `xattrs`; xattr rows have exactly `name`, `value_b64`, with strict base64 bounded to 64 KiB decoded per attribute. Supported names are `security.selinux`, `system.posix_acl_access`, `system.posix_acl_default`; unsupported security metadata blocks installation rather than being dropped. Permission/owner fields are bounded non-bool integers; ordering and absence are preserved and independently read back.
- `source-control-adapter-original-membership`: keys `schema_version`, `purpose`, `object_id`, `identity`, `controller_path`, `ancestor_states`. Identity is the task layout above; `controller_path` is a normalized absolute v1 freezer path restricted to the guest's recorded original owned fixture hierarchy or its controller root. Ancestor rows contain `controller_path`, `self_state`, `effective_state`; states use the exact freezer enum. Original paths are rollback data only and cannot expand establishment mutation scope. Missing/substituted ancestors or state drift rejects reversal.
- The journal record purpose is `source-control-adapter-journal`, with exact keys `schema_version`, `purpose`, `context`, `sequence`, `previous_ref`, `operation`, `phase`, `state`, `before_refs`, `readback_ref`. Sequence is a positive non-bool integer; `previous_ref` is null only at sequence one; phase is `intent` or `readback`; readback_ref is null only for intent. Valid transitions are compiled and every readback must reference its preceding intent in the same generation. Sequence/hash-chain gaps reject recovery. A detached caller-provided release-authority file is not sufficient: it must bind actual current fictional operator state and a release decision held by the trusted harness.
- `source-control-adapter-result`: keys `schema_version`, `purpose`, `context`, `operation`, `state`, `evidence_refs`, `blockers`, `enforcement_complete`, `real_execution_ready`. State uses exactly `draft`, `prepared`, `establishing`, `held`, `lost`, `recovery-required`, `released`; blocker rows have `object_id` (nullable), `reason_code`. Both readiness flags are always false. These are two-family rehearsal states, not global production states.

Reference graphs are slot-typed and acyclic. Opaque raw originals must still be ordinary bounded private files with their original-byte digest; they are not recursively parsed as JSON. Context copies must match exactly, including boot/generation. Sort set-like rows and blockers deterministically; retain original request/evidence bytes for lineage. No wall time substitutes for monotonic freshness, and no host clock is compared directly to guest monotonic time.

Fixed guest roots are `/var/lib/paymenter-adapter-rehearsal/<guest_id>/` and its private subdirectories. Scheduler installation is limited to newly owned `/etc/cron.d/paymenter-fixture-<guest_id>` and an owned fixture-user spool. Service/timer/boot units are newly owned `paymenter-fixture-*` units generated by code. All fixture executable paths are compiled beneath the guest root. The sole mutable freezer subtree is `/sys/fs/cgroup/freezer/paymenter-fixture-<guest_id>/`; the controller/observer and unrelated workload remain outside it. A request's `relative_path` never expands these roots.

The guest root is an independently booted disposable guest, not a chroot over production or a privileged container mounting host control files. Dispatcher admission checks the runtime, QEMU guest UUID, bootstrap identity and nonce established by Task 1 before resolving scope. This is a trusted harness/guest boundary, not resistance to malicious host or guest root. A caller-selected `fictional=true` flag is insufficient. Fixture setup/failure injection uses a separate `source-control-adapter-scenario-request` with exactly `schema_version`, `purpose`, `guest_id`, `session_id`, `scenario_id`; scenario IDs are compiled from the spec matrix, with no path/command/argument field. `OwnedGuest.run_case(scenario_id: str) -> dict` sends that request. It cannot extend the six adapter operation names or reach production resources.
