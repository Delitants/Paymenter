# BIND restricted SSH integration (0.1.0)

This native `Others/Bind` extension manages explicitly approved customer zones through a root-owned, view-bound helper. It does not replace a DNS manager, install itself, discover/adopt all zones, or delete zones through billing events. All bindings and DNS mutations default to disabled. Existing billing remains with the incumbent system until its separate handover.

## Package and dependencies

The helper requires Python **3.11+**, dnspython **2.9.0**, idna **3.20**, OpenSSH, sudo and compatible installed BIND utilities. `tools/bind-helper/package-manifest.json` pins every runtime module, the hashed dependency lock and installation templates. From the helper directory, `python -I -m paymenter_bind.qualify` audits an installed package; from a source checkout use `python -B -m paymenter_bind.qualify` with that directory as the working directory. Qualification is local source integrity, never native acceptance or installation authority. Verify the source/manifest against the reviewed commit through an independent trusted channel; an attacker replacing both defeats a standalone checksum.

Prepare dependencies in an isolated, root-owned virtual environment using `pip install --require-hashes -r requirements.lock` from reviewed wheels. Do not change system Python. Build tooling in `pyproject.toml` is for development; native installation should copy only manifest-verified `paymenter_bind/` into the isolated environment's site-packages, avoiding an unreviewed build-isolation dependency download. Inventory the environment and wheel hashes in the private execution packet. Do not install or upgrade any runtime automatically to make an incompatible server pass.

## Required private inventory before installation

Prepare and review a concrete packet separately. The example `tests/native-acceptance.example.json` deliberately has no target, key, view, zone or authority and **cannot authorize execution**. Record:

- Exact primary/secondary host identities, independently verified host-key fingerprints, dedicated SSH accounts, separate integration key fingerprints, approved source address and key custody. The operator's existing SSH identity stays on their workstation.
- Installed BIND version, exact executable identities and actual `rndc zonestatus/reload/notify/reconfig`, `named-checkzone`, `named-checkconf` and `named-compilezone` syntax. Prove view-qualified selection and all dynamic/signing flags; absent flags fail closed. Modern BIND documentation is not proof for an older installation.
- Python/runtime/dependency identities; OS and BIND service account; effective UID/GID; service/chroot layout; SELinux/AppArmor policy; transfer ports and existing transfer authentication. Secondary raw-file conversion must be qualified against the installed utility and format.
- Exact view/class, canonical domain, immutable application binding UUID and verified service/owner evidence on **both** endpoints. Pin that the same UUID maps to the same domain on each endpoint; requests cannot select a domain or view. The complete default denylist must cover infrastructure/reverse zones. Adopt no zone based on a service label or numeric legacy ID alone.
- Exact root-owned configuration, managed include hook, zone directory/data owner, journal/backup directory, free space and readback permissions. Directory traversal denies symlinks, nested mounts and group/world-writable ancestors; ordinary files must have one link. Secondary BIND-owned data must meet these custody rules. An incompatible legacy directory needs a separately reviewed layout change.
- PHP/FPM, proxy and HTTP request deadlines for the **whole action**. One SSH call is bounded at 40 seconds ordinary/70 seconds lifecycle; a create action can perform two lifecycle calls and two inspections sequentially, so allow at least 220 seconds plus application overhead (or keep lifecycle preparation disabled until a reviewed background-worker design exists). Client record save/reconciliation can use two inspections plus a mutation, so allow 120 seconds plus overhead. Disconnects preserve an uncertain reference; never automatically retry mutations.
- Exact preimages, file ownership/modes/hashes, loaded serials and authoritative snapshots for all protected customer/infrastructure zones; server-only backup/recovery custody; exact newly owned files and key removal rollback list. Never copy production recovery keys to the workstation.

## Proposed installation layout (not an installer)

The fixed wrapper expects `/opt/paymenter-bind/venv/bin/python3`; the package must be importable under `-I`. Config is fixed at `/etc/paymenter-bind/server.json`, inside a root-owned mode0700 directory; the file is root-owned mode0600 and single-link. Root-only state is `/var/lib/paymenter-bind/state` in the template. Pin actual data paths/UIDs/view/include in the private packet. Root-owned binaries and configuration cannot be writable by the restricted SSH user.

Review `install/paymenter-bind-helper` and `install/ssh-dispatch`, install them only at their fixed `/usr/local/libexec/` paths, then validate the exact no-argument `sudoers.example` with the installed `visudo` before installing. `authorized_keys.example` requires a **new dedicated key**, `restrict`, a fixed forced command and source-address restriction. Deny password/interactive access for this account using the reviewed host SSH policy. No shell/SFTP/SCP, PTY, agent/X11/port forwarding or generic sudo/rndc access is allowed. Test those denials using the actual installed SSH service; template inspection does not prove them.

Leave `server-config.example.json`'s empty allowlist unchanged until exact bindings have independent approval. Per-binding entries contain only `zone`, exact `view`, `role` (`primary`/`secondary`), relative `file`, `uid`, `gid`, root-owned `managed_include`, and closed `operations`. Global fixed command/config paths, protected suffixes, TTL range and peer addresses are administrator settings. New-zone creation requires a managed include hook already installed in precisely that view; runtime never edits the main config. Primary transfer/notify permission is confined to the configured secondary; secondary masters and any transfer key stay server-side. Preserve existing-zone transfer/authentication policy. No open AXFR is introduced.

In Paymenter, install the extension through native extension management only after a separately approved DB migration, configure dedicated encrypted private keys and independently pinned public host keys, keep `operations_enabled=false`, and leave all bindings disabled. Keys use full audit redaction; private transport files use app-owned0700 directories/0600 files and exact expired-file cleanup. Do not paste private keys into tickets, logs or version control. A host-key mismatch always fails; there is no trust-on-first-use customer action.

Administrators need explicit `admin.bind.view`, `.approve`, `.inspect`, `.prepare` or `.reconcile` permissions. Create an immutable domain/service binding and independently verify ownership before approving it. Approval leaves customer access disabled. Migration actor/owner/service holds continue to deny customer reads/writes; administrator inspection is separately permissioned and read-only. Shared account members inherit the existing native service update permission, not a new write grant.

## Request states and recovery

The closed `paymenter-bind-v1` contract has UUIDs, 32KiB input, 1MiB output, 100 changed RRsets, 500 total zone records, 2MiB zone files, 30-second ordinary and60-second lifecycle helper budgets. Only A, AAAA, CNAME, MX, TXT, CAA and SRV RRsets are editable. Preserve unrelated ordinary RRsets. SOA/NS edits, dynamic journals, signing/inline-managed data, includes, generate directives and unsupported constructs fail closed.

Every write retains an exclusive claim, exact preimage/candidate and terminal receipt. Lost responses or crashes after install remain `uncertain`; the application blocks new writes until the original reference is reconciled with `inspect_request`. Refreshing or logging back in preserves that reference. Never replace it with a new mutation UUID. A helper cannot prove an interrupted request safe merely from the currently loaded serial; preserve evidence and resolve privately. A changed expected revision rejects without writing and asks the customer to review refreshed data.

A successful primary update plus secondary lag is `pending_replication`: “Your DNS update was saved. The secondary nameserver is still updating.” Read-only status checks do not replay it. Resolver caches may retain previous values until TTL expires; that is distinct from nameserver replication. Failed reload attempts a guarded rollback only if the exact candidate is still present, restores prior RRsets with a **newer** SOA serial and verifies reload/readback. Never restore an old serial or overwrite an external update. Partial cross-host creation is retained for explicit administrator recovery, never automatically deleted.

## Native acceptance and rollback gate

After separate approval, use exactly **one disposable domain** confirmed absent from all customer/infrastructure zones. Record exact helper/key/include/config ownership before the test. Verify actual forced-command/no-argument denial, wrong host-key refusal, cross-binding/view denial, primary create and multi-address edit/readback, TXT/IDNA behavior, guarded rollback, secondary transfer/convergence, and unchanged protected files/configuration/loaded serials. Bound each attempt and retain failure receipts; any uncertainty closes that attempt rather than permitting an automatic write retry.

Revocation removes only the exact dedicated authorized-key entry and disables Paymenter operations/bindings; it does not restart BIND or delete zones. Rollback may remove only exact newly owned installation/test-zone artifacts whose current hashes/ownership still match the reviewed packet. Restore unrelated include/config preimages only through a separately reviewed BIND validation/reconfiguration action, never an unverified blind copy. Preserve journal/backups and application operation history. Disable the extension instead of running a destructive uninstall.

Local Python/PHP tests use temporary files, a disposable guarded DB and fake BIND/SSH responses. Desktop/mobile fixture rendering is synthetic. These checks establish neither installed SSH restrictions nor native BIND/provider/customer acceptance. Customer activation, recovery refresh and billing handover are separate gates.
